# 段落角色判定规则

## 核心原则：先定角色，再排版

**脚本不猜语义，只按角色渲染。** 角色由人工或 AI 判定后显式写入 `type` 字段。

`"1."` 既可能是三级标题，也可能只是一条编号的工作事项。靠编号前缀自动判断会把整段叙述误加粗——
**漏加粗只是不够醒目，误加粗是整段错误的视觉噪音**，两者代价不对称。

## 角色清单

| type | 含义 | 版式 | 是否加粗 |
|------|------|------|---------|
| `heading1` | 第一层 `一、` | 黑体 三号 | 否 |
| `heading2` | 第二层 `（一）` | 楷体 三号 | 否 |
| `heading3` | 第三层 `1.` | 仿宋 三号 | **是** |
| `heading4` | 第四层 `（1）` | 仿宋 三号 | **是** |
| `heading5` | 第五层 `①` | 仿宋 三号 | **是** |
| `body` | 普通正文（无编号） | 仿宋 三号 | 否 |
| `numbered_body` | **编号正文**：带编号，但内容是工作事项而非标题 | 仿宋 三号 | **否** |
| `blank` | 空行 | — | — |

兼容旧名：`level1`~`level5` = `heading1`~`heading5`；`text` = `body`。
未知 `type` 一律按 `body` 处理（安全默认）。

> `numbered_body` 是这套规则的关键：它保留编号、按正文排版、不加粗。
> 工作总结、情况汇报里「1. 完成了……，开展了……」这类罗列几乎都属于它。

## 判定依据（按可靠性排序）

1. **Word 语义标记**（最可靠）
   - `w:outlineLvl` 有值 → 对应层级
   - 样式名为「标题 N」/「Heading N」→ 对应层级
   - 用 `scripts/inspect_docx.py` 可直接读出

2. **上下文结构**
   - 该段独立概括、后面另有段落展开说明 → 更像标题
   - 该段直接叙述工作内容（完成了/开展了/组织/落实……）→ 更像编号正文

3. **句法特征**
   - 以句号、分号、叹号、问号结尾 → 是完整句子，判 `numbered_body`
   - 不以句末标点结尾 → 可能是标题

4. **原文加粗**（**仅作弱参考**）
   - 原格式本身可能有误，不能因为原文加粗就判为标题，反之亦然

## 不用字数阈值

长度不是可靠信号：短的可能是标题，也可能是简短事项；长的可能是标题，也可能是长句叙述。
用长度硬切会在边界处随机出错。以「是否成句」和「上下文」判断，比数字数可靠。

## 存疑处理

拿不准时：**默认按 `body` / `numbered_body` 处理**（保留编号、不加粗），并把疑问集中列出供确认。

输出格式：

```markdown
以下段落角色存疑，请确认（未确认的按正文处理）：

| 段落 | 原文 | 建议 | 疑问 |
|------|------|------|------|
| 第15段 | 1. 工作目标 | heading3 | 无句号，可能是标题，也可能是省略标点的短事项 |
```

`scripts/inspect_docx.py` 会自动生成 `_uncertain` 列表，可直接转为上表。

## 不自动改动编号

编号属于原文内容。脚本**不得**改写、补全、重排序号。
编号格式错误（如 `1、` 应为 `1.`）只在用户明确要求时按 `numbering-rules.md` 修正，并单独报告。

## 完整流程

```bash
# 1. 提取原文 + 样式线索 + 角色建议
python3 scripts/inspect_docx.py 原文.docx -o content.json

# 2. 人工/AI 审阅 _uncertain 列表，定稿 type

# 3. 按角色渲染
python3 scripts/generate_gongwen.py --config content.json --output 公文.docx
```

第 2 步不可省略——`inspect_docx.py` 给的是**建议**，最终判断在人。
